# 知更·Paper 产品改版方案

版本：讨论稿 v1.0｜2026-09-29

## 1. 判断与定位

现有产品以“配置论文参数 → 规划章节和字数 → 生成整篇论文提示词 → 复制到外部 AI”为主线，另有论文审阅、写作优化和指南。这套流程能帮助用户组织指令，却没有保存一篇论文的文献、证据、论点与正文之间的关系。当前仓库的论文信息和章节主要保存在运行时状态中，`localStorage` 主要用于主题和指南偏好；用户无法把一次研究当作可反复进入的项目。生成器的“版本 B”允许模型依据训练知识列参考文献，虽然附带核实提示，仍会把未经验证的条目带进写作流程。

**新版定位：一个以文献和证据为中心、由作者掌控写作的轻量论文工作台。** 用户在这里整理资料、搭建论证、写作和检查来源；AI 只帮助完成有明确输入、可核对的具体任务。

第一批目标用户是正在写课程论文、毕业论文或文献综述的中文写作者，尤其是已有一些资料、但难以把资料变成结构化论证的人。先服务单人写作，不同时扩展通用内容创作。

### 用户与要完成的事

| 用户情境 | 典型困难 | 产品应帮助完成的事 |
| --- | --- | --- |
| 课程论文：时间有限，已有少量文献 | 大纲先于阅读形成，正文出现空泛论断 | 快速把每节论点连到实际读过的材料，看到缺口。 |
| 毕业论文：资料多、周期长 | 摘录分散，数周后找不到原文 | 在项目中保存证据、原文位置和自己的解释。 |
| 文献综述：观点相互冲突 | 很难按主题比较研究，不宜逐篇流水账 | 用“支持 / 反驳 / 背景”把证据组织到同一问题下。 |

产品目标是让作者在写作过程中能回答三个问题：**这个主张的依据是什么？依据来自哪一处原文？哪些地方还需要查证？** 首版的成功不以生成字数衡量。

## 2. 核心工作流

1. **建立项目**：记录题目、研究问题、论文类型、目标读者、引用格式和截止日期；允许先填最少信息，写作中再补。
2. **收集文献**：导入 BibTeX、RIS，或手动录入 DOI、题名等元数据；给每条文献记录摘要、阅读状态、关键发现、局限和原文定位。导入的元数据需要人工核对，尤其是作者、年份、页码和版本。
3. **制作证据卡**：一张卡对应一条可引用的发现或引文，包含来源、页码或段落、摘录、自己的解释，以及证据类型。卡片可标记“支持 / 反驳 / 背景 / 待核实”。
4. **搭建论证大纲**：章节不再只分配字数；每节明确要回答的问题、拟提出的主张、关联证据和仍缺少的材料。保留拖拽排序和可选字数目标。
5. **分节写作与核查**：作者在编辑区分节写作，把证据卡插入草稿。检查面板列出未关联证据的结构化主张、缺少原文定位的证据卡、正文引用目标不存在、已收录但未引用的文献。对于自由文本中的“关键事实缺来源”，首版只提供人工检查清单，不假装规则能理解全部语义。检查结果是待人工确认的提示，不能宣称自动判断真伪。
6. **导出与继续编辑**：导出 Markdown、项目备份 JSON 和 BibTeX / RIS 参考文献文件。Word 文档导出可在后续版本增加。

### 首版主界面

- 左侧：项目、章节与进度。
- 中间：当前章节的主张、证据卡和正文编辑。
- 右侧：当前章节可用文献、引用详情和待核查项。
- 顶层仅保留“资料 / 大纲 / 写作 / 检查”四个目的明确的入口；设置放入项目菜单。

### 关键交互

- 用户可从空项目直接建立第一节，不因题目或投稿场合未填而受阻。
- 在文献详情选中一段摘录后创建证据卡；卡片默认回链该文献，原文位置由用户填写或确认。
- 在大纲的某个主张下添加证据时，显示证据所支持或反驳的关系；同一证据可关联多个主张。
- 正文中的引用显示文献简称，点击后看到完整元数据、相关证据和原文位置。
- 检查面板每条提醒都有“前往处理”“标记已核对”，并明确它是规则检查还是人工确认项。

## 3. 功能取舍

| 现有模块 | 首版处理 | 理由 |
| --- | --- | --- |
| 论文参数 | 改为项目设置 | 保留必要约束，降低开工前填写成本。 |
| 大纲管理 | 保留并扩展 | 章节应连接研究问题、主张和证据；字数只是参考。 |
| 生成提示词 | 收纳到具体任务 | 提供“总结这几张证据卡”“检查这节论证”等可复制指令，不再把生成整篇论文作为主按钮。 |
| 论文审阅 | 改为证据与引用检查 | 优先指出可定位的缺口，并提供原文位置供作者复核。 |
| 写作优化 / 去 AI 味 | 移入可选语言润色 | 重点改进清晰度、准确性和作者风格；不以规避检测为产品承诺。 |
| 写作指南 | 改成按步骤出现的帮助 | 在用户做任务时解释术语和下一步，不长期占用大块工作区。 |

## 4. 首版范围与边界

### 必须交付

- 多项目创建、编辑、自动保存、删除与本地备份恢复。
- BibTeX / RIS 导入与手动添加文献；重复 DOI 和重复题名提醒。
- 证据卡与文献、章节的双向关联；支持原文定位和“待核实”状态。
- 分节大纲和 Markdown 正文编辑；正文引用可回到对应证据卡。
- 可解释的规则检查：缺失来源、无定位、未使用文献、引用目标不存在。
- Markdown 正文、BibTeX / RIS 参考文献与项目 JSON 导出；清楚说明数据存储在当前浏览器。
- 备份导入前展示项目名、条目数量和冲突处理方式；原项目不会被静默覆盖。

### 后续迭代

- PDF 文本提取、页码定位与批注导入，需要先验证不同 PDF 的解析质量。
- DOI 元数据检索、Zotero 同步、CSL 样式化参考文献。
- 可选 AI 服务接入、多人协作、跨设备同步和 Word 导出。

首版不自动搜索并认定“真实参考文献”，也不自动生成整篇可直接提交的论文。对不确定的来源只显示“待核实”，并保留原始输入。文献元数据正确不等于某个论断得到文献支持；证据卡必须由作者确认内容与主张的关系。

### 优先级

| 级别 | 能力 | 放在这个级别的原因 |
| --- | --- | --- |
| P0 | 项目保存与备份、文献导入、证据卡、论点关联、分节编辑、引用回链、基础检查 | 组成可实际使用的完整闭环，任何一项缺失都会让资料与正文脱节。 |
| P1 | 文献去重细化、批量编辑、写作任务提示词、阅读进度、更多导出格式 | 提升效率，但可以等闭环稳定后加入。 |
| P2 | PDF 解析、Zotero 同步、模型接入、协作与云端同步 | 依赖外部服务、复杂文件或账户系统，需要单独验证。 |

首版建议保留无需登录、无需提供 AI API 密钥的使用方式。可选 AI 操作把选中的主张和证据卡整理成可复制的任务说明；输出必须标明所用材料，并允许用户逐条核对。AI 生成的推断不自动成为证据卡。

## 5. 技术实现建议

沿用现有 Preact 与 Vite 静态站点，避免为了改版先引入服务端。以 IndexedDB 保存项目、文献、证据卡、章节和正文，`localStorage` 仅保留界面偏好。项目数据采用稳定 ID，并记录创建、修改时间与数据格式版本；导入时先校验，再预览合并结果。提供显眼的“导出备份”和“恢复备份”，因为浏览器本地数据可能被用户清理，也不会天然跨设备同步。

建议实体关系：`Project → Section → Claim`，`Reference → Evidence`，`Evidence ↔ Claim`，正文引用连接到 `Reference` 或 `Evidence`。引用检查从这些明确的关联生成，所有警告都应能跳转到对应位置。

需要定义几个数据约束：证据卡只能引用项目中存在的文献；删除文献前列出受影响的证据和正文引用；导入重复条目时保留用户已有笔记；导出的项目 JSON 包含格式版本号，恢复时迁移旧版本数据。自动保存应有清楚的状态反馈，保存失败时提示用户导出备份。

隐私说明应如实描述本地存储边界：资料保存在当前浏览器配置文件中，清理浏览器数据可能删除项目；复制提示词到第三方 AI 后，材料将按该服务的规则处理。若未来接入模型 API，要在发送前列出将传出的具体内容。

互操作先选 BibTeX 与 RIS，符合常见文献管理软件的导出格式；将来需要 Zotero 集成时可参考其 Web API。DOI 元数据补全可在下一阶段研究 Crossref 等服务的覆盖率、调用限制与浏览器跨域情况，不把网络服务设为离线首版的前提。

## 6. 衡量与验收

**核心衡量**：用户能否在一个项目里完成“文献 → 证据 → 主张 → 正文引用 → 回查原文”闭环。早期先采用任务观察，不急于埋点收集研究文本。可记录用户是否完成、哪里放弃、是否误以为“元数据已验证”就等于“论断已验证”。若要采集匿名使用数据，先提供清楚的告知与选择。

用三项真实任务检验首版，而不是只看按钮是否可用：

1. 用户能导入一组文献、找到重复项，打开某条记录核对来源字段。
2. 用户能把至少两张证据卡关联到一个章节主张，回到正文时仍能找到原文定位。
3. 用户能发现并处理一处“结构化主张缺证据”和一处“引用目标不存在”，随后导出完整项目并在新浏览器环境恢复。

特别检查刷新、浏览器关闭后重新打开、重复导入、损坏备份、长篇正文和窄屏下的数据完整性。首版发布前做一次小规模任务观察，记录用户卡住的位置和误解的提示，再调整工作流。

发布门槛：三项任务都能从头到尾完成；项目刷新后内容仍在；备份可在干净环境恢复；检查提醒能回到具体对象；文献删除与导入冲突不会悄悄丢失用户写下的内容。

## 7. 实施顺序

1. 做数据模型和本地保存，完成项目、文献、证据卡的最小闭环。
2. 把现有大纲升级为“主张—证据”结构，并加入正文编辑。
3. 做引用关联、规则检查、导出与恢复。
4. 迁移原有的参数、审阅及提示词功能，作为相关步骤的辅助工具。
5. 用真实任务验证后，决定 PDF、Zotero、AI 接入的优先级。

每一步都应保留一个可演示的端到端场景。最早可用版本以手动添加文献和证据卡起步；BibTeX / RIS 导入、恢复与冲突处理完成后再开放给更广泛用户。

当前运行态的论文参数和大纲没有持久化项目数据可供自动迁移。实现新版时可继续读取现有主题等界面偏好；对于旧单文件版本的用户数据，应先确认是否存在其他保存途径，再决定是否需要专门的导入器。
